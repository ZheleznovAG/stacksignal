# Состояние и точка продолжения

[Документация](README.md) · [Миссия](MISSION.md) · [Архитектура](ARCHITECTURE.md)

Контрольная точка: **22 октября 2026**. Описан проверяемый исходный код рабочего дерева.
Перед продолжением выполните `git status --short` и `git log -5 --oneline`: наличие
функции в локальном дереве само по себе не определяет состояние удалённой ветки.
В публичном ZIP Git-истории нет: оценивайте переданный снимок, не предполагая, что он
совпадает с удалённой веткой.

## Что работает

| Область | Текущее поведение |
| --- | --- |
| Сбор | GitHub, Hugging Face, arXiv, npm и PyPI; поисковые запросы проектов, обновление находок, релизы и зависимости |
| Проекты | Ручное создание, безопасное сканирование README/манифестов и папки с несколькими проектами, проверяемый импорт |
| Понимание проекта | Сохраняемая техническая модель: цели, подсистемы, возможности, пробелы, потребности и необходимые предшествующие задачи |
| Сопоставление | Эвристики и отдельные AI-оценки, включая релевантность конкретному проекту; происхождение оценки отображается |
| Поиск в чате | Локальные ключевые слова/FTS5 BM25 и необязательные ONNX-эмбеддинги; объединение ранжирований через RRF |
| Решения | Голоса, заметки, решения по проектам, история и поводы пересмотреть решение при новых данных |
| Проверки кандидатов | Сохранённое задание с исходным контекстом, копирование/Markdown, начало/отмена проверки, итог и свидетельства |
| Актуальность | Изменение требований/контекста отмечает старые оценки и проверки; устаревшее подтверждение не разблокирует зависимые задачи |
| AI | Необязательный отдельный HTTP-шлюз либо экспорт/применение пакетов локальным агентом |
| Эксплуатация | Единый `stacksignal.py`, ограниченные зависимости, диагностика и SQLite backup; личное состояние можно вынести из репозитория |

Сервис рассчитан на одну локальную установку и один процесс. Новая установка пустая.
AI по умолчанию выключен. Прямое подключение произвольного model API требует адаптера
к текущему контракту шлюза. Выполнение подготовленного задания происходит во внешнем агенте.

## На чём остановились

Завершён путь «потребность → кандидат → задание для агента → записанный итог». Реальная
проба на небольших вымышленных данных продемонстрировала, что рекомендацию нужно проверять:
один инструмент связывания сущностей дал ложные объединения при автоматической настройке.
Частные исходные данные, отчёты и названия личных проектов в публичную поставку не входят.

Текущий аудит добавил переносимый запуск и документацию, исправил работу резервной копии
с конфигурацией базы и обработку устаревших предварительных результатов. Подробности,
метод проверки и границы аудита находятся в [AUDIT.md](AUDIT.md).

## Следующая продуктовая задача

**Улучшить отбор кандидатов для конкретной потребности.** `needs.shortlist()` сейчас
использует совпадения слов/фраз и ограниченный список. Существующий семантический поиск
чата ещё не подключён к этому отбору. Некоторые реальные потребности остаются без
кандидатов, даже при большом общем каталоге.

Ожидаемый следующий результат:

1. Воспроизводимый набор потребностей с ожидаемыми релевантными ответами, независимыми от текущих AI-оценок.
2. Сравнение существующего отбора с добавлением поиска по смыслу и вариантами формулировок.
3. Несколько обоснованных кандидатов либо объяснимый результат «подходящих нет»; ограничения и источники сохраняются.
4. При нехватке покрытия — адресные поисковые запросы по потребности с учётом бюджетов источников.

Эта задача **ещё не реализована**. Подробный контракт изменений следует выводить из
указанных модулей и нового набора оценки, не из предположения, что семантическое сопоставление уже везде работает.

## Дальнейшие направления

- Запуск Claude/другого агента из интерфейса: сохраняемые задания, прогресс, отмена и продолжение после лимитов/перезапуска.
- Первый запуск с демонстрационным проектом и проверка сценария на добровольных внешних пользователях.
- Независимая оценка полезности рекомендаций. Текущий `eval-retrieval` использует голоса/решения и допускает AI-fallback; это ограниченный диагностический отчёт.
- Надёжное восстановление длительных фоновых задач после аварийного завершения. Контрольные точки сбора уже существуют; общей постоянной очереди заданий нет.
